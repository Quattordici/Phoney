# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Phoney is a .NET fake-data library (targets net8.0 and net10.0) built on the locale data of faker.js.

## Guidelines

The solution should strive to follow best practices and follow well established patterns like SOLID and DRY. It should use a TDD workflow. Focus should be on performance, easiness of use and robustness. Functionality should support source generation and AOT as much as possible.

In practice here:

- **TDD:** write the failing test first, make it pass, then refactor. Run the one test (see Commands) before the whole suite.
- **Source generation and AOT:** every feature that touches object generation must work through both the reflection model and the source-generated one, with identical data for a seed, and must not add trim/AOT warnings. Reflection-only entry points carry `RequiresUnreferencedCode`/`RequiresDynamicCode`; `Fake.Generated<T>()` is the unannotated facade entry for types with a generated model. The reflection model builds collections through the same typed `FakeScope` helpers as generated models (`ReflectionCollections`), never per-element reflection.
- **Performance:** lookups are array-indexed, hot paths are allocation-free, templates are parsed once. Check `benchmarks/` when touching them.
- **Ease of use:** one obvious call for the common case (`Fake.Populate(x)`, `faker.NationalId.Person()`), sensible defaults, and a clear exception message that says how to fix the problem.
- **Robustness:** validate arguments, never fail silently, and make results reproducible for a seed.

## Commands

```bash
dotnet build -c Release                  # warnings are errors (Directory.Build.props); public members need XML docs
dotnet test                              # all test projects; runner is Microsoft.Testing.Platform (global.json), tests use TUnit + Shouldly
dotnet test --project tests/Phoney.Tests -- --treenode-filter "/*/*/PopulateTests/Keeps_what_is_set_and_fills_the_rest"   # one test
dotnet test --project tests/Phoney.Tests -- --treenode-filter "/*/*/NationalIdTests/*"                                      # one class
dotnet test --project tests/Phoney.NodaTime.Tests                                                                            # one add-on (also .DependencyInjection/.EntityFrameworkCore/.SourceGenerator/.TUnit)
dotnet publish tests/Phoney.AotSmoke -c Release -p:TreatWarningsAsErrors=true   # Native AOT: trim/AOT warnings must stay at zero
dotnet run -c Release --project benchmarks/Phoney.Benchmarks -- --filter '*'
```

- Tests target only net10.0 locally; CI (`GITHUB_ACTIONS=true`) adds net8.0. CI also runs the AOT publish and executes the binary. On a Mac the link step can fail with `library 'ssl' not found` (then `brotlienc`) because Homebrew's libs are not on the linker path; prefix the publish with `LIBRARY_PATH=/opt/homebrew/opt/openssl@3/lib:/opt/homebrew/opt/brotli/lib` (needs `brew install openssl@3 brotli`) and run `artifacts/aot/Phoney.AotSmoke`. The compile step before the link is what reports AOT warnings.
- Locale data is refreshed with `cd tools/extract && npm install --save-exact @faker-js/faker@latest && node export-locales.mjs ../../data/raw`, then `dotnet run --project tools/Phoney.DataCompiler`, then `dotnet test`. CI fails if `data/`, `src/Phoney/Resources`, `src/Phoney/Data/Generated` or the README locale table differ from a fresh import, so never hand-edit those.

## Architecture

**Data pipeline.** faker.js locales → `data/raw/*.json` (Node, `tools/extract`) → `tools/Phoney.DataCompiler` → Brotli resources `src/Phoney/Resources/Locales/*.bin.br` (embedded) + generated integer key catalog `src/Phoney/Data/Generated/DataKeys.g.cs`. The compiler validates every `{{…}}` template against each locale's fallback chain. At runtime `LocaleStore` loads a locale lazily and flattens its fallback chain (`locale → … → en → base`) into one array, so a lookup is an array index. Modules read data by `DataKeys.*` integer keys, not strings. **Start-up is part of the design:** `LocaleResource.Open` decompresses a file and makes one pass that only records where each string and entry starts; `LocaleData.Get` decodes an entry (and the strings it uses) the first time its key is read, and the merge asks `LocaleResource.Has`, so a process that uses a few dozen keys never builds the rest. The first call of a process is dominated by JIT, so avoid on that path: big static initialisers (use one string parsed lazily, like `CharMappings`, or per-module registration, like `TemplateFunctions`), `Regex` (hand-written loops, see `InternetModule.RemoveInvalidEmailChars`), `FrozenDictionary` construction, and `ConcurrentDictionary.Count/Keys/Values` (they take all locks and initialise an EventSource; `KeyRegistry` keeps its own counters). `benchmarks/Phoney.Benchmarks.Comparison` has `cold`, `cold-phases` (time and JIT per step of the first call) and, published with `-p:AotComparison=true`, the same `cold` for Native AOT; measure with them before and after touching this path.

**Values.** `Faker` (per-locale, owns a `Randomizer`, a seeded xoshiro256**) exposes lazily created modules (`src/Phoney/Modules`, one per faker.js module plus `NationalIdModule`). `Fake` is the thread-safe static facade over a per-thread `Faker`. `ReferenceDate` resolves as: explicit value > `TimeProvider` > `DefaultSeededReferenceDate` when seeded > system clock, so seeded dates don't drift. `IFaker` mirrors every public member of `Faker` (a test enforces it): add new modules/methods to both. Anything that draws randomness must draw from the faker's `Randomizer`, and **the order of draws is part of the contract**: existing seeded output must not change, so new randomness goes after existing draws (see `PersonModule.Profile`).

**Object generation.** `Generator<T>` is immutable (every method returns a copy) and runs against a `FakeModel<T>`, which describes members and how to create/read/set them. Two implementations produce **identical data for the same seed**: `ReflectionModel` (compiled delegates, annotated `RequiresUnreferencedCode`/`RequiresDynamicCode`) and models emitted by `src/Phoney.SourceGenerator` for `[FakeFor<T>]` (registered through `ModelRegistry` by a module initializer; AOT/trim safe). Rules, conventions and nullability/annotation constraints are applied in `FakeScope.Get`, which both paths must call for every member. Explicit rules bind to the root type, and members of nested objects through path rules (below); custom conventions (`WithConvention`, then `Fake.Conventions`) also reach nested objects through `GenerationSettings.Conventions` (`NestedConventions`, slots bound per nested type and cached). Name conventions live in `Generation/Shared/ConventionRules.cs`, which is **compiled into both the runtime and the netstandard2.0 generator** (keep it free of newer APIs); `ConventionValues` turns a `ConventionKind` into a value. Append new `ConventionKind` values at the end of the enum (generated code embeds the numeric values). `Identity` (in `FakeScope.cs`) is the lazy per-object person/address/timeline so first name, email, birthdate, age and national id of one object agree. `Populate` is one shared algorithm (`Populator`) over the model's `Get`/`IsUnset`/`Set`/`Fallback` hooks, so reflection and generated models fill objects the same way. **Member types**: scalars are `TypeCategory`s (append new ones, like `ConventionKind`; `ConventionRules.CategoryOf` names them, `ConventionValues` makes the value, `ModelBuilder.NonNull` emits the call, `Boxed` is the reflection twin; numbers go through `Number<T>` generic math). Closed generic classes are nested objects like any other (`IsNestable` / `IsNestedType` exclude only framework types and open generics). Tuples (`ValueTuple`/`Tuple` up to 7) and `KeyValuePair` are built part by part, in order, by the names `Item1…` / `Key`, `Value` (`CompositeParts` in both models; the generator emits `new ValueTuple<…>(…)` inline), `Memory<byte>` and `T[,]` likewise (`FakeScope.Array2`). A framework struct without a producer is its default value in both models, a framework class `null`. A root type asked for directly (`Fake.One<int>()`) is produced like a member when `ReflectionTypeModel.RootValue` knows it. Do not generate types whose values depend on the machine (`CultureInfo`, `TimeZoneInfo`): seeds must give the same data everywhere.

**Normal distribution.** `Randomizer.Normal` is Box–Muller with exactly two draws and no cached state (item *n* stays stable under reseeding), and its logarithm and cosine are `PureMath` (series using `+ - * /` only): `Math.Log`/`Math.Cos` call the platform's libm, which may round the last bit differently, and seeded data must be identical on every OS (a test pins exact bits that were also reproduced in Python). Do not use `Math.Pow`/`Exp`/`Log`/`Sin`/`Cos` for generated values; `NumberModule` rounds with a table of powers of ten for the same reason. `Number.Normal` (truncation by drawing again, then clamping after 100 misses) and `Normal<TNumber>` (rounding, type limits through `CreateSaturating`) build on it, and `Generator<T>.WithNormal` is `With(member, faker => faker.Number.Normal<T>(…))` with the arguments validated when the rule is added, so reflection and generated models agree; it is in `StrictAnalyzer.MemberRules` and `UsageAnalyzer.RuleMethods/SlotRules`.

**Feeds.** `DataFeed` (public, `Phoney` namespace) reads a CSV or flat JSON array completely and validates its shape; `Generator<T>.WithFeed` stores a `FeedSettings`, and `Compile` (`ApplyFeed`, before the convention step so the feed beats conventions and `WithType`, and after explicit rules, which win) converts each column once to its member's type with `FeedValues.Convert` (so bad values fail with row and column at first use, not mid-run) and installs a `RuleKind.Convention` slot that reads the row from `FakeScope.Index` (`InOrder`: modulo; `Random`: a hash of the base seed and the index), so draws are untouched and item *n* is stable. A generator with a feed is refused as a nested generator (`CannotBeNested`), and `StrictAnalyzer` skips chains with `WithFeed` because the columns are only known at runtime.

**Read-only collections.** A public get-only (or private-setter) property or readonly field whose type `CollectionTypes.IsFillable` (the generator mirrors it in `ModelBuilder.FillableCollections`) accepts becomes a `FakeMember` with `FillsExisting` (not settable) **appended after all other members**, so its draws come last and existing seeds don't move; fields come before properties within a type, the order reflection gets from metadata tokens, and the generator copies it. `Create` produces the collection through `scope.Get` like any member (rules, `Ignore`, constraints, path rules, `CollectionSize` all apply) and adds it with `FakeScope.AddAll` (emitted in generated `Create`, a compiled delegate from `CollectionFillers` in reflection); `FakeModel<T>.Fill` does the same for `Populate` (empty ones; `All` replaces) and for `CreateWith` objects. Members that are constructor parameters or settable are never also filled. `Generator.Compile` rejects object-dependent rules on them, and the EF add-on ignores the ones that are navigations. **Member order** (constructor parameters, then writable members, then these) is the same in both models: base class first, within a class all fields then all properties, each in declaration order. That is what the reflection model gets from sorting by metadata token (the token tables of fields and properties don't interleave), and `ModelBuilder.InReflectionOrder` copies it for the generator; `MemberOrderTests` pins it, so don't sort by declaration order in one model only.

**Back-references.** `Generator<T>.WithBackReferences()` runs `BackReferences.Apply` on the finished object (after dependent rules, before `AfterCreate`/`Where`; also after `Populate`): it walks the graph through settable members with `IFakeModel.GetMember/SetMember` (the models of the objects' runtime types, so reflection and generated models agree; constructor-only members are unreadable and skipped) and sets each `null` object member to the nearest ancestor its type accepts. It draws nothing, so seeds are unchanged.

**Collections.** `CollectionTypes` is the one table of generated collection shapes: each is built like `List<T>`, `HashSet<T>` or `Dictionary<K,V>` (`CollectionKind`, so draws are identical whichever type holds the elements) and converted when the member's type is another one. Reflection converts with a delegate compiled once per member by `CollectionConverters` (a static factory such as `ImmutableArray.CreateRange`/`ToFrozenSet`, else a constructor taking the built collection); generated models call `FakeScope.ListAs/SetAs/DictionaryAs` with a conversion lambda that `ModelBuilder.OtherCollections` emits. Add a shape in all three places (the table, the converter's factories if it isn't constructor-based, `OtherCollections`) and to `CollectionShapeTests.Catalog`. A default `ImmutableArray<T>` refuses to enumerate, so `FakeScope.IsEmpty` treats that as empty.

**Subtypes.** Interfaces and abstract classes are generated through `FakeScope.NestedObject`, which picks a subtype before the model lookup: the generator's `Subtype<TBase, …>()` (travels in `GenerationSettings.Subtypes`, merged with `Fake.Subtypes` in `Generator<T>.Compile`), then `Fake.Subtypes` (sorted by full name so registration order never changes draws), then `[JsonDerivedType]` defaults (`Subtypes.DefaultsOf`; the generator registers them via `ModelRegistry.RegisterDerivedTypes`, reflection reads the attributes). No subtype → `null` with no draw, one → no draw, several → one `Random.Index` draw. `[FakeSubtype<TBase, TSub>]` makes the generator emit the model and a `Fake.Subtypes.Add` in the module initializer.

**Path rules.** `With/WithOneOf/Ignore/Invalid/Boundary(x => x.Billing.City)` and `x => x.Lines.Each().Sku` (`FakePath.Each` is only an expression marker; `Dictionary.Values` and `Nullable.Value` are skipped) store a `PathSpec` in `Config.PathRules` (key: the dotted names; `AddRule` sends single names to `Rules` as before, and rejects object-dependent rules on paths). `Compile` builds a trie of `PathNode`s with `PathRules.Build`, which also validates every path against the models (declared types, collection element types; below an interface/abstract class it stops). The runtime needs to know **which member of the parent a nested object is created for**: `FakeScope.Get` stores `_member`, and `NestedObject` (called inside that `Get`, also for collection elements) looks up `_children[_member]`, binds the node to the nested model once per type (`PathNode.Bind`: the `NestedConventions` slots with the path rules on top, shared and stateless) and gives the child scope the node's children. So reflection and generated models agree without model changes, and `Billing` and `Shipping` of the same type are different positions. Objects made by `Use`/`Fake.Generators`/a member generator bring their own rules and ignore path rules; `PopulateNested` (existing objects) doesn't use them. `RuleSelector` in the generator reads the same paths for PHONEY007/008 and strict mode (a nested rule covers no member of the generated type).

**Type generators.** `Generator<T>.Use<TNested>(generator)` / `Use<TBase, TGenerated>` register an `INestedGenerator` per type in `GenerationSettings.TypeGenerators` (null when empty). `FakeScope.NestedObject` is the single hook, so reflection and generated models agree without model changes: after the depth check it looks for a generator of the declared type (`FindGenerator` walks the scope chain, the innermost registration wins, so a type generator's own graph still sees the outer ones), else resolves the subtype and looks again for the picked type, else uses the model. Cycle checks run against both the requested type and `INestedGenerator.GeneratedType`. Member rules are resolved earlier in `FakeScope.Get`, so they win. `Fake.Generators` (`FakeGenerators`, like `Fake.Subtypes`) registers the same thing app-wide: `Generator<T>.Compile` merges `FakeGenerators.All` with the generator's own `Use`s (own wins) and `ArgumentGenerator` takes the snapshot too. Scalars and arrays are rejected in `Use`/`Add` (`NestedGenerators.ValidateType`) because they never reach `NestedObject`. `Populate` only uses the generators for nested objects that are missing; existing ones go through `PopulateNested`.

**Invalid and boundary data.** `Generator<T>.Invalid/Boundary(member)` add a `RuleKind.Constraint` rule; `Compile` resolves it against the member's `FakeMember.Constraints` through `ConstraintCases` (internal; the one place that knows how each annotation is broken or hit), so reflection and generated models agree because both describe members with the same constraints. A case is a `Func<FakeScope, Func<FakeScope, object?>, object?>` that **always runs the member's normal producer first** (so later members draw the same randomness as in a valid object) and then replaces or reshapes the value; collections instead set `FakeScope.ForceNextCollectionCount`, consumed by the first `CollectionCount`. Format/pattern violations are chosen by running the real `ValidationAttribute`s on candidate texts (no value is invented that the validators accept). `InvalidCases()`/`BoundaryCases()` derive one generator per case from the same base seed. Keep `StrictAnalyzer.MemberRules` and `UsageAnalyzer.RuleMethods/SlotRules` in sync when adding such rules (PHONEY004/007/008). `CollectionTypes` is the single definition of what is generated as a collection.

**Conditions, positions and rule verification.** `Generator<T>.Sequence/Cycle(member, …)` add a `RuleKind.Convention` rule whose factory reads `FakeScope.Index` (the root object's position in the sequence, kept by `Where` retries), marked `Positional`; nested objects are always position 0, so `INestedGenerator.CannotBeNested` makes `With`/`Use`/`Fake.Generators.Add` refuse a generator that has positional rules (or verifies rules). `Generator<T>.Where(x => x.Member, condition, maxAttempts)` stores a `MemberFilter` in `Config.MemberFilters`; `Compile` puts it on the member's `RuleSlot` (`Filter`/`FilterAttempts`, creating a `Default` slot after the strict check so a filter alone doesn't count as coverage) and `FakeScope.Get` draws the member again (together with `Unique`, the smallest limit applies). It throws at `Compile` for members that are ignored, dependent, created by `CreateWith`, or generated from the per-object `Identity` (`IdentityBound` kinds: a retry would return the same cached value). `Generator<T>.Where(predicate, maxAttempts)` stores a `Filter` in `Config.Filters`; `Run.Create`/`Run.Populate` own the retry loop, so nested generators (`CreateNested` goes through `Run.Create`) filter too and models need no change. Attempt 0 reseeds exactly like an unfiltered run (an accepted object is the object you would get without the condition); attempt *k* reseeds with `DeriveSeed(itemSeed, k)`, so results depend on seed, position and attempt only. The limit is the smallest `maxAttempts` of the filters. `Populate` supports filters with `PopulateMode.All` only (kept values can't be regenerated, `MissingOnly` throws before touching the object), and `Cases()` (Invalid/BoundaryCases) strips filters and verification. `VerifyRules()` sets `Config.Verify`; `Compile` then creates a `RuleUsage` (in `GenerationSettings.Usage`, null otherwise so nothing is paid) and registers this generator's own graph-dependent rules: path rules (`PathRules.Build` registers while building the nodes; `PathNode.Create` marks when it binds an object, which is when the rule applies), `Subtype` (marked where `NestedObject` finds the registration), `Use` (marked in `FindGenerator`) and `WithConvention` (marked when `Compile` or `NestedConventions.Bind` matches it). App-wide registrations (`Fake.Subtypes`, `Fake.Generators`, `Fake.Conventions`) are not tracked, and neither are rules for the root's own members (always applied). `Generator<T>.VerifyUsage` throws after `Generate`/`GenerateParallel`/`Populate` when something is unused (never for zero objects); `Stream()` throws `NotSupportedException`, and a generator that verifies can't be given to `With`/`Use`/`Fake.Generators.Add` (`NestedGenerators.RejectVerification`, via `INestedGenerator.VerifiesRules`), because nothing would check it. A new kind of graph-dependent rule must register in `RegisterUsage` and mark at the place it takes effect. The first run publishes its compiled state with `State.Publish` (`Interlocked.CompareExchange`), so racing first runs share one `Compiled` and usage and `Unique` sets are never split between copies.

**Seeds for replayable tests.** `FakeSeed` (core) reads `PHONEY_SEED` and makes new seeds. `Phoney.TUnit`'s `[FakeSeed]` implements `ITestRegisteredEventReceiver` and installs a `SeededTestExecutor` (the executor, not start/end receivers, because it must open the `Fake.Seeded` scope in the same async flow as the test body and sees the failure itself); `SeededRun.Execute` holds the logic apart from TUnit so it is unit-tested. `IScopedAttribute` makes the method attribute win over class and assembly. A test has one executor (`SetTestExecutor` replaces), so the attribute has `Order = int.MaxValue` (registers last) and passes `DiscoveredTest.TestExecutor` as `inner`, which runs inside the seeded scope; a test pins this with `[TestExecutor<T>]` in both attribute orders. `[FakeData]` stays deterministic (stable derived seed) and only moves with `PHONEY_SEED` (`FakeDataAttribute.ResolveSeed`).

**Adapted scalars (NodaTime).** `ConventionRules.AdaptedCategoryOf` maps known add-on types (`NodaTime.Instant` → DateTimeOffset…) to the category conventions are matched with. Values come from the add-on: generated models call `Phoney.NodaTime.NodaTimeValues.<Type>(scope, kind, constraints)` when the add-on is referenced, reflection uses `ScalarAdapters` (filled by the add-on's static constructor, loaded on demand). Without the add-on both paths keep the old nested-object behavior. Adapted types are never `IsNested`.

**Strict analyzer.** `StrictAnalyzer` (PHONEY004, in `Phoney.SourceGenerator`, shipped in the Phoney package) mirrors `Generator<T>.Compile`'s strict check for fluent chains that start a generator and end in `Generate`/`Stream`/`GenerateParallel`/`Populate`; it reuses `ModelBuilder.DescribeMembers`. Keep it in sync when strict rules change. Register new diagnostics in `AnalyzerReleases.Unshipped.md` and the README diagnostics table. Advisory rules (analyzers) use the category `Phoney.Usage` (`Diagnostics.UsageCategory`), generator diagnostics `Phoney`, so users can switch the advisory ones off together; `DiagnosticCategoryTests` pins this.

**Usage analyzer.** `UsageAnalyzer` (PHONEY005–008, same assembly) reports calls that silently do nothing or throw at the first `Generate`: discarded results of the immutable `Generator<T>` (and of `Populate` on structs), undisposed `Fake.Seeded` scopes, rules for members `Generator<T>.Compile`/`MemberName` reject, and rules replaced later in the same chain (PHONEY008 also covers a `Use`/`Subtype` for a type that an earlier call of the same method in the chain registered; both checks share `HasEarlierInChain`). `RuleSelector` (in `AnalyzerSupport.cs`) reads a rule's `x => x.Member` selector and is shared with `StrictAnalyzer`; keep the PHONEY007 checks in sync with `Generator<T>.Compile`. `[FakeSubtype]` with an abstract type or interface is PHONEY009 and is not registered (the module initializer would throw). The same analyzer reports PHONEY010 (constant seed in a loop; the `foreach` collection and `for` initializers run once and are not flagged) and PHONEY011 (constant arguments the runtime rejects: keep in sync with the argument checks in `Generator<T>`). `ModelSuggestionAnalyzer` (PHONEY012, Info) suggests `[FakeFor<T>]` for reflection use; it replays `ModelBuilder` over every `[FakeFor]`/`[FakeSubtype]` owner (source, and referenced assemblies that reference Phoney) to know which types have models, and may not call `Compilation.GetSemanticModel` (RS1030).

**Code fixes.** `src/Phoney.CodeFixes` (netstandard2.0, packed next to the analyzers in the Phoney package, no dependencies) holds `MakePartialCodeFix` (PHONEY001) and `AddFakeForCodeFix` (PHONEY012). It is a separate assembly because analyzers must not reference the Workspaces assemblies; the IDE provides them. Tests (`CodeFixTests`) run the fixes in an `AdhocWorkspace` via `CodeFixHarness`.

**When the model contract changes** (new `FakeModel<T>` member, `FakeMember` argument): update `ReflectionModel.cs`, `Emitter.cs`/`ModelBuilder.cs` in the generator, and review then accept the snapshot (`tests/Phoney.SourceGenerator.Tests/Snapshots/*.received.cs` → rename to `.verified.cs`). The test `Generated_and_reflection_models_produce_identical_data` and the Populate parity test guard the two paths.

**National ids.** `NationalIdScheme` pairs a generator with a validator per country and kind; `NationalIds` is the registry (schemes in `src/Phoney/NationalIds`). Every scheme must have a validator so tests can assert generated values.

**Templates.** `Template`/`TemplateFunctions` evaluate `{{module.method(args)}}` (case-insensitive, faker.js names plus .NET names); register new module methods in `TemplateFunctions.Modules.cs`.

**Packages.** `Phoney` (with the generator, analyzers and code fixes packed inside, no dependencies), `Phoney.TUnit`, `Phoney.Xunit` (xUnit.net v3), `Phoney.NUnit` and `Phoney.MSTest` (`[FakeData]`, built on `ArgumentGenerator`; the settings, the stable derived seed and the `PHONEY_SEED` move are `FakeDataOptions` in core, so a change to the seed formula would move the data of every test in every framework and a test pins it; these attributes fill method parameters, TUnit also constructors and properties; each framework attribute re-declares the five option properties because attributes can't share a base), `Phoney.DependencyInjection` (`AddPhoney`, scoped `IFaker`, `IFakerFactory`, singleton generators; a container `TimeProvider` is used unless it is `TimeProvider.System`), `Phoney.EntityFrameworkCore` (`HasFakeData`; EF Core 8 for net8.0 and 10 for net10.0 via conditional `PackageVersion`s; post-processes navigations, max lengths, keys and foreign keys from EF metadata), `Phoney.NodaTime` (`faker.Noda()` and adapted members). Each package has its own README (packed) and test project, and is packed in `ci.yml`. **Dependency floors** are the lowest versions whose build and tests pass (found by building the library against the floor and running the tests with the framework at the floor and at the newest: xunit.v3 3.0.0, NUnit 4.0.0, MSTest 4.0.0, TUnit.Core 1.10.0, NodaTime 3.1.0), set as `*Floor` properties in `Directory.Packages.props`; test projects use the newest frameworks (`*Latest`, through `xunit.v3`, `MSTest`, or `VersionOverride="$(...TestVersion)"` where library and tests share an id: NUnit, NodaTime, TUnit). `-p:TestAgainstFloors=true` switches the five integration test projects (`dotnet test --project tests/Phoney.Xunit.Tests -p:TestAgainstFloors=true`, also Phoney.NUnit/MSTest/TUnit/NodaTime) to the floors, and the `floors` job in `ci.yml` runs them that way and checks the floors were really resolved. Raise a floor only when the code needs a newer API (the job then fails), and re-run the experiment when changing it.

## Conventions

- Tests use TUnit (`[Test]`, `[Arguments]`) with Shouldly. New checksum/format logic should be verified against an independent implementation (the national id schemes were cross-checked with `python-stdnum`), not only against itself.
- Generated values must be reproducible: no `System.Random`, `DateTime.Now`, `Guid.NewGuid` or unordered iteration in generation paths; use the faker's `Randomizer` and `ReferenceDate`.
- The build enforces parts of this for `src/**`: `src/BannedSymbols.txt` (BannedApiAnalyzers, RS0030) bans `System.Random`, `DateTime`/`DateTimeOffset` clocks, `Guid.NewGuid` and `Environment.TickCount`. A deliberate use (the system-clock fallback, the random base seed of an unseeded generator) needs `#pragma warning disable RS0030 // reason`. `.editorconfig` also makes the performance rules (CA18xx…) and the culture rules (CA1304/1305/1309–1311) warnings for `src/**`, so new code must pass them or justify a suppression. `tools/Phoney.DevAnalyzers` (not shipped, referenced by `src/Directory.Build.props`) reports PHONEYDEV001 for `foreach`, spreads and order-sensitive LINQ over `HashSet`, `Dictionary`, the concurrent/immutable/frozen dictionaries and sets and their `Keys`/`Values`: sort first (`Order`/`OrderBy` with an ordinal comparer), keep an ordered list next to the set, or `#pragma warning disable PHONEYDEV001 // why the order can't matter`. It doesn't see interfaces (`IDictionary`, `ISet`), so review those.
- `Phoney` and `Phoney.DependencyInjection`/`Phoney.NodaTime` are `IsAotCompatible`. `Phoney.EntityFrameworkCore` and `Phoney.TUnit` use reflection by design (`HasFakeData`, `[FakeData]`), so they only enable the trim/AOT analyzers and annotate or justify each reflection use; don't claim AOT compatibility for them.
- README is user-facing documentation for every feature (add-on packages also in their own `src/<Package>/README.md`) and also contains the generated locale table between `<!-- locales:start/end -->` markers. Keep `samples/Phoney.Samples` showing the core features.
